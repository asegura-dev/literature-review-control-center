# ADR-0008 - No AI co-authorship in the repository; disclosure of AI use in publications

## Context and Problem Statement

LRCC is developed with the help of an AI coding assistant, working inside defined limits with a
person as the gate between phases. Such assistants commonly add attribution to what they produce:

- `Co-authored-by:` trailers in commit messages;
- "Generated with …" footers in commits and pull requests;
- session identifiers as trailers.

They are also usually configured through tool-specific files in the working directory.

Authorship carries responsibility: an author answers for the work. A tool cannot, and research
publishing policies (for example the positions of COPE and the ICMJE) state that AI tools do not
qualify as authors, and that their use should be disclosed.

Two questions follow:

- What may the public repository say about who wrote it?
- Where is the use of AI disclosed?

## Decision Drivers

- The maintainer is the sole author and is responsible for every line.
- A rule that relies on remembering it will eventually be broken. It needs mechanical
  enforcement where enforcement is possible.
- Disclosure of AI use in publications should follow the venue's policy, honestly.
- The public repository is a reproducibility record, not a record of the tools used to type it.

## Considered Options

1. **Policy plus enforcement:**
   - no attribution to an AI anywhere in the repository or its history;
   - no assistant-specific configuration in the repository;
   - a `commit-msg` hook and a CI check that reject attribution;
   - disclosure of AI use in publications, following each venue's policy.
2. Policy only, written in the contributor documentation.
3. Allow attribution trailers, and disclose in the repository as well as in publications.

## Decision Outcome

Chosen option: **option 1**.

- **No attribution in the repository.** No commit, pull request, tag, release note, `CITATION.cff`
  entry or document names an AI tool as author or co-author. No `Co-authored-by:` trailer, no
  "Generated with" or "Generated by" line, no session-identifier trailer.
- **No assistant-specific files in the repository.** The assistant's operating instructions and
  permission settings live in the maintainer's private folder, next to the checkout and outside
  it, not in the repository. The same applies to the founding documents that describe the
  working method with the assistant by name.
- **Enforcement in two places:**
  - a `commit-msg` hook, run by pre-commit, rejects any message containing a `Co-authored-by:`
    trailer or a "Generated with" or "Generated by" line;
  - because a local hook can be skipped, CI repeats the same check over every commit in a pull
    request.
  The patterns are generic and name no vendor.
- **Human co-authors.** The hook rejects every `Co-authored-by:` trailer, human ones included.
  LRCC has one author today. When a person co-authors a commit, this record is amended to allow
  named human co-authors, instead of weakening the pattern quietly.
- **Disclosure in publications.** A paper that uses LRCC states in its methods or
  acknowledgements, as the venue requires, that AI coding assistance was used to develop the
  software, and that the author reviewed and is responsible for it. The exact wording follows
  the venue's policy at the time of submission.

### Consequences

- Good, because the repository's history names only the person responsible for it.
- Good, because a slip is stopped by a machine twice, locally and in CI, instead of being
  noticed later.
- Good, because disclosure happens where it matters for research integrity: in the publication.
- Bad, because the repository itself does not say that AI assistance was used. A reader of the
  code alone will not learn it. That is a deliberate choice, and the strongest objection to this
  record: some readers would consider a disclosure in the README the more transparent option.
- Bad, because pull request bodies and release notes are written outside git, so the hook cannot
  see them. They are covered only by review.
- Bad, because rejecting every `Co-authored-by:` trailer is broader than the rule needs, until
  the amendment for human co-authors.

### Confirmation

- `.pre-commit-config.yaml` contains the `commit-msg` hook.
- The CI workflow contains the commit-message check.
- The phase notes of v0.0.1 record a test commit with a `Co-authored-by:` trailer being rejected
  by the hook, with its output.
- `git ls-files` lists no assistant-specific configuration file.

## Pros and Cons of the Options

### Option 1 - Policy plus enforcement

- Good, because it is enforced where it can be and honest in publications.
- Bad, because the repository is silent about AI use, and PR bodies are unchecked.

### Option 2 - Policy only

- Good, because it needs no hook.
- Bad, because assistants add these trailers by default, and a rule nobody checks is broken the
  first time someone is in a hurry.

### Option 3 - Allow attribution, disclose everywhere

- Good, because it is maximally transparent about the tools.
- Bad, because it presents a tool as a co-author, which authorship policies reject and which the
  maintainer does not accept.

## More Information

- COPE, "Authorship and AI tools" (position statement), and the ICMJE Recommendations, section on
  AI-assisted technologies. Both should be reread when a paper is submitted, since venue policies
  change.

## Implementation

- **v0.0.1.** `scripts/check_commit_message.py` holds the patterns, with tests for what it
  rejects and what it lets through. It is run as the `no-ai-attribution` `commit-msg` hook in
  `.pre-commit-config.yaml`, and by the `commit-messages` job in
  `.github/workflows/quality-gate.yml` over every new commit of a push or a pull request. Direct
  pushes to `main` are covered as well as pull requests, because the maintainer pushes directly.
- The hook was seen to reject a message with a `Co-authored-by:` trailer, naming the line. The
  output is in `docs/phases/v0.0.1.md`.
