# Phase notes - v0.5.0, Stored runs

Branch `v0.5.0-runs`. Decision: ADR-0012, accepted on 2026-09-30, building on ADR-0004. What was
run is kept apart from what is assumed; every run below was on Windows 11, Python 3.12.13,
uv 0.10.12.

## What "done" means for this phase

From the roadmap: real counts are recorded with their date and query version. **That needs a
real run, which only the maintainer makes. Until then this phase is built, not done.**

## Observed

### Stored runs, against the mocked transport

- A stored response file equals the mocked answer byte for byte, and its SHA-256 and size match
  the log entry.
- Two runs are chained: the second entry names the first one's hash.
- A count edited directly in the database makes `status` report that the log does not verify,
  and exit with code 1.
- A run that retrieved 2 records of 57 reported is marked incomplete, and says so.
- `--preview`, a failed search and `status` each leave the review's folder holding only
  `protocol.yaml`.

### Two defects the existing tests caught

- **A mock that was not realistic.** With paging, the arXiv adapter asks for more pages until it
  has what was reported. A preview test answered every request with the same two-entry page, so
  the adapter collected 20 copies. The adapter was right and the mock was wrong: a real source
  answers with an empty page past its last result. The mock now does the same.
- **A run identifier split in two.** `status` first drew a table. At 80 columns the table
  wrapped the run identifier over two lines, so it could not be found in the output. `status`
  now prints one line per run.

### The real commands, without the network

Run through `.\run.ps1 run lrcc`, against the development workspace in a temporary directory.

Review example.

The run log verifies: no entry was edited.

> lrcc search example --source pubmed          (configuration without a network section)
error: the network is off, so nothing was requested
  - set network.enabled to true in the configuration to allow requests

After both, the review's folder held only `protocol.yaml`.

## Assumed, not yet observed

- **A real run.** No request was made to PubMed or arXiv. The adapters, the paging and the
  stored responses were exercised only with synthetic answers.
- **Paging against the real arXiv API.** The loop ends on an empty page or when it has what was
  reported. How the real service behaves at the end of a long result set was not measured.
- **DuckDB reading this file in a later version.** It is a premise in the roadmap, to check
  before relying on the database as a long-term record.
- **CI for this branch.** It runs when the pull request is opened.

## Pending, outside this phase's scope

- **PubMed beyond 10,000 results.** `esearch` returns at most 10,000 identifiers; more needs
  NCBI's history server. Until then such a run is stored as incomplete.
- **Checking the stored files against the log.** `status` verifies the chain, not the files on
  disk. That is `verify`, in v0.7.0.
- **A run folder that no log entry names**, left if the database write fails after the files
  are written. `verify` should report it.
- **The tags `v0.0.1`, `v0.1.0` and `v0.3.0`** wait for their commits to reach `main`.
