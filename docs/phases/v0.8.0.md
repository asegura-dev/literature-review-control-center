# Phase notes - v0.8.0, Scopus and IEEE Xplore

Branch `v0.8.0-scopus-ieee`. Decisions: ADR-0015 and ADR-0016, proposed on 2026-09-30, and
accepted the same day, after the first real requests with the maintainer's keys. What was run is
kept apart from what is assumed; every run below was on Windows 11, Python 3.12.13, uv 0.10.12.

## What "done" means for the two parts built

The first part, from ADR-0015:

- keys come from the `.env` beside the configuration and reach the sources;
- no key is ever kept in anything LRCC stores or prints;
- Scopus and IEEE Xplore search, check gold works and replay like the other sources.

The second part, from ADR-0016:

- a database's RIS export enters the review as a run, stored, verified and replayed like an API
  search;
- a truncated export, or one imported twice, never passes silently.

The roadmap's full v0.8.0 also asks for records found by other methods, and for notifying long
runs. Those remain.

### No key is kept

- Stored IEEE Xplore and Scopus runs were made with fake keys against the mocked transport. Every
  byte in the review's folder was then read, response files and database included, and none of
  the fake keys was there. Neither was any of them in the command's output.
- The recorded IEEE Xplore address ends with `apikey=[redacted]`. Scopus keys travel in headers,
  so its recorded addresses carry no key at all.
- An answer that repeated the key was refused, with nothing stored. An error answer holding the
  key was quoted with the key replaced.
- A `.env` placed anywhere but beside the configuration, even in the workspace, was not read:
  the command named the missing key and the file that should hold it, and made no request.
- A replay ran after the `.env` was deleted, with no request.

### A defect the new tests found in all three paging sources

Scopus's last page, in the synthetic answers, reported a total of zero. The adapter took the
count from the last page it read, so the run reported 0 of 3. arXiv and IEEE Xplore had the same
pattern. All three now keep the count from the first page: the count the source reported when
the search began.

### A `# noqa` that was taken out again

While wiring the keys, a `# noqa` was written into the configuration loader to silence an
`assert`. Adding one needs the maintainer's approval, so the code was restructured instead, and
no `# noqa` or `# type: ignore` exists in `src/`.

### The first requests with real keys: both refused

On 2026-09-30 the maintainer ran a preview and a gold check on each new source, with their own
keys in the `.env` beside their configuration. Both services refused the key:

- IEEE Xplore answered HTTP 403, `Developer Inactive`.
- Scopus answered HTTP 401, `APIKEY_INVALID`, "The provided apiKey is invalid."

Each command quoted the answer and stopped, and no key appeared in the output. The client retries
only transport errors, 429 and 5xx, so each command made a single request.

Scopus's answer says a key reached it; IEEE Xplore's does not show that by itself. LRCC never
sends a request without a key, because a missing key stops the command first, and it sends the
IEEE Xplore key as `apikey`, the parameter IEEE's documentation names. Checked on the LRCC side,
without opening the `.env`:

- the tests assert the exact key each request carries, in the query for IEEE Xplore and in the
  header for Scopus;
- the parser removes surrounding spaces, matching quotes, a byte-order mark and Windows line
  endings;
- none of the four key variables was set in the user's or the machine's environment, so no
  other value overrode the file.

What the answers mean was first read from published documentation:

- `Developer Inactive` is what the API gateway IEEE Xplore uses answers for a key that has not
  been approved, or has been disabled. IEEE issues keys during US Eastern business hours, Monday
  to Friday, and a registration is confirmed from an e-mail IEEE sends. The same day, the
  maintainer found the key's status on IEEE's developer portal to be "waiting": not yet approved,
  as the answer said.
- `APIKEY_INVALID` says that Elsevier does not recognise the value as a key. It is a different
  refusal from a missing institutional entitlement, which concerns authorisation. This is not
  yet confirmed.

### Scopus accepted the key: the STANDARD view answers, the COMPLETE view is refused

Later the same day, at the maintainer's request, the preview and the gold check were run again
with the maintainer's keys. They ran in a scratch workspace, on copies of the draft protocol
(version 4, the same SHA-256 as the maintainer's) and of the gold set. IEEE Xplore answered
`Developer Inactive` once more. Scopus accepted the key:

- The preview asks for the COMPLETE view, and was refused: HTTP 401, `AUTHORIZATION_ERROR`, "The
  requestor is not authorized to access the requested view or fields of the resource".
- The gold check asks for counts in the STANDARD view, and ran:

| Source | Gold works | Retrieved | Missed | Not indexed | Unknown |
|---|---|---|---|---|---|
| Scopus | 14 | 12 | 0 | 0 | 2: works known only by arXiv id |

So the key works, and the draft Scopus string retrieves every gold work that Scopus can be asked
about. The COMPLETE view is the one that carries the abstracts screening needs.

### The second part: `lrcc import`

Built the same day, from ADR-0016, because the maintainer works from outside the institution's
network and IEEE Xplore's key awaits approval. The databases' web interfaces export the same
search, with abstracts, as RIS.

- **Each new check was broken on purpose, and a test failed each time.** The checks were: the
  canonical form of old entries, the refusal of a double import, the refusal of a future day and
  its day of tolerance, the refusal of a file cut short, the EID rule, and the replay of an
  import.
  - The first attempt at the cut-short mutation added a line before the refusal and left the
    refusal in place, so no test failed. The mutation was at fault, not the tests. Redone to
    remove the refusal, it was caught by the reader's tests and by the command's.
- **Old logs still verify, checked against real bytes.** A run was stored in a scratch workspace
  with the code of the last commit, which writes v0.7.0's format, from the synthetic arXiv
  answer. With the new code:
  - `status`, `verify` and `replay` accepted it;
  - after an export was imported into the same review, all three accepted both runs, and the
    replay was identical for each;
  - importing the same file again was refused, naming the run that holds it.

### IEEE Xplore, once its key was active: a gold check that could not miss

Later the same day the key's status turned "active". At the maintainer's request, the preview and
the gold check were run again in the scratch workspace, on protocol version 6. Its IEEE Xplore
string is the same as version 4's.

- **The preview** was accepted, string length included, and IEEE Xplore reported 500 records.
- **The first gold check** read 6 works as retrieved, 6 as not indexed (all from publishers IEEE
  Xplore does not hold) and 2 as unknown (arXiv identifiers only). No work was missed.
- **A control showed the check could not miss.** It ran on two works: a gold work, and an
  unrelated IEEE article (ResNet, `10.1109/CVPR.2016.90`). Both read as retrieved. With the
  `doi` parameter, the API ignores the string.
- **The DOI as a field inside the query.** Three requests were made, outside LRCC's commands,
  through its own client:

  | Question asked in `querytext` | Records | Expected |
  |---|---|---|
  | `("DOI":<unrelated>)` | 1 | 1 |
  | `(<string>) AND ("DOI":<unrelated>)` | 0 | 0 |
  | `(<string>) AND ("DOI":<gold work>)` | 1 | 1 |

- **The adapter now asks that way**, and its test asserts that the `doi` parameter is never
  sent. Rerun with the fix:
  - the control read the gold work as retrieved and the unrelated article as missed, and exited
    with code 1;
  - the gold set again read 6 retrieved, 0 missed, 6 not indexed and 2 unknown. This time the
    6 retrieved mean the string finds them.

All of this spent fewer than 60 of the day's 200 IEEE Xplore calls.

## Assumed, not yet observed

- **Scopus granting the COMPLETE view** from the institution's network or VPN. The requests above
  came from outside it, and there it was refused.
- **IEEE Xplore's count of exactly 500.** A round number is worth confirming: against the web
  interface, or by the stored run, which pages through every record.
- **A DOI with parentheses or quotes** in IEEE Xplore's `("DOI":...)` field. No gold work has one.
- **A real RIS export from Scopus or IEEE Xplore.** The reader is tested against synthetic files.
  Two things in them rest on documentation and common exports, not yet on a file from the
  maintainer: the tags each database writes, and Scopus's link carrying the EID.
- **CI for this branch.**

## Fixtures

All five fixtures are new and synthetic: written by hand, with invented titles, authors, numbers
and DOIs. The maintainer reviews them before they are committed.

- `tests/fixtures/ieee_search.json`, `scopus_search.json` and `scopus_empty.json`: only their
  shape follows the services' answers, and each carries a `_synthetic` field saying so.
- `tests/fixtures/scopus_export.ris` and `ieee_export.ris`: only their shape follows each
  database's RIS export, and each record says so in its `N1` note.

## Pending, outside these parts

- **Records found by other methods**, such as citation searching. PRISMA 2020 counts them apart
  from database searches, so their import needs a way to say which they are.
- **CSV and BibTeX exports, and databases without an adapter**, such as Web of Science: a
  protocol names only the four known sources.
- **`check-query` against an imported run.**
- **ADR-0013 has no Implementation section.** The records' README asks for one once a record is
  built. ADR-0014 and ADR-0015 lacked one too, and got it when the maintainer accepted them.
- **Notifying long runs** (ntfy).
- **An e-mail for NCBI**, which asks tools for a contact address.
- **Scopus's STANDARD view as a declared fallback** if the institution does not grant COMPLETE.
  It would be a decision, not a silent retry, because STANDARD carries no abstracts. An export
  from the web interface now covers the same case, with abstracts.
